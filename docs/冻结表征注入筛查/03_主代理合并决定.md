## 2. 主代理核验与裁决

### 2.1 三方一致的部分

- 候选 B 与现有预测端残差代数同构：满行秩时 `W_H W_H⁺ = I`，估计量严格化为 `st_pairwise_delta_forecast`，**NO-GO**（设计与审查一致，主代理确认）。
- 候选 C 是"输入端专家 + 预测端专家"的样本级路由，等价于 MoE 路由换名，且两条专家分支的有效容量之和无法在 NC13 下被匹配，**NO-GO**。

### 2.2 分歧点与裁决依据

设计方主张：PTI 能表达"邻站上下文与中心表征的交互项"，而出口加性修正在代数上不能；故存在可分离机制。
审查方主张：该分离只对一个**刻意受限的加性 PTO** 成立；若把输出侧控制放宽到同时读取 `(x, c)` 的等容量 side-network，同一交互项可被表示，因此仍落在条件 prompt/adapter 一族。

主代理核验后采纳审查方意见，理由有两条独立证据：

1. **代数层面**：混合差分 \(I_f=f(x_a,c_a)-f(x_a,c_b)-f(x_b,c_a)+f(x_b,c_b)\) 只能排除 \(F(x)+g(c)\) 这类严格加性形式；它不能排除 \(F(x)+r(x,c)\)。而输出侧控制只要允许读取中心表征与邻站上下文（例如把冻结层摘要与门控上下文拼接后送入一个小型残差头）即可产生非零 \(I_f\)。
2. **代码层面**：现有预测端分支已经具备这种结构。`ST_PatchTST_model.py:379-382` 计算 `forecast_features = torch.cat([pooled_context, recent_context], dim=1)`，而 `use_forecast_confidence` 打开时（`ST_PatchTST_model.py:387-393`）进一步用中心站摘要 `center_summary` 门控修正量，即预测端修正本身已经是 \(r(x,c)\) 形式。设计方所声称的"输出侧只能加性"与实际实现不符。

因此"入口注入 vs 输出注入"在本项目内**不是可分离机制**，而是同一条件适配族中的注入位置选择；按 `00_探索边界.md` 的硬约束 4（必须与最强同信息集现成方法不同构）与硬约束 5（NC13 等容量特异性门），候选 A 判定 **NO-GO**。

### 2.3 关于那条实证线索

匹配组件消融观察到的"最优注入位置随训练协议/任务变化"（冻结 168→6：输入端 +2.25% 优于预测端 +0.42%~+0.67%）仍然成立，但：

- 它来自 3 种子、test 划分的探索性运行，不足以支撑机制主张；
- 本轮证明它不能被包装成"函数类可分离"的机制；
- 作为**描述性消融结果**写入论文是恰当的（"注入位置在不同训练制度下的排序不同，我们将此留作开放问题"），不应声称为创新点。

## 3. 阶段决定

**Round 15 理论阶段 STOP。** 不创建实验分支，不实现 PTI/PTO，不消耗任何种子或时间片，b2/b3 等保留资源保持封存。
