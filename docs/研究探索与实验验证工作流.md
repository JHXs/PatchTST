# 研究探索与实验验证工作流

## 1. 目的

本工作流用于后续模型改进研究，将“理论可行性探索”“实现与消融”“独立确认”分开，避免在理论尚未明确时过早修改正式模型，也避免根据确认结果反复调参。

Git 分支和 Herdr worktree 提供代码与资料的物理隔离，但不能代替实验设计上的独立性。数据边界、候选选择、随机种子、指标和放行规则仍需预先固定。

## 2. 推荐分支结构

```text
main
├── research/<idea>-theory
├── experiment/<idea>-ablation
└── experiment/<idea>-confirmation
```

三个分支的职责如下：

| 分支 | 起点 | 用途 | 禁止事项 |
|---|---|---|---|
| `research/<idea>-theory` | `main` | 文献、开源实现、理论推导、可行性和风险分析 | 不开展正式模型实验，不根据测试集形成方案 |
| `experiment/<idea>-ablation` | 最新稳定 `main` | 实现候选、单元测试、冒烟测试、训练集/验证集选择和消融 | 不把探索性测试结果包装成独立确认 |
| `experiment/<idea>-confirmation` | 消融分支中选定的固定 commit | 用冻结结构、配置和新种子进行最终确认 | 不因确认结果修改结构或超参数后重复使用同一确认数据 |

`<idea>` 使用简短、稳定的英文 kebab-case 名称，例如 `adaptive-lag-fusion`。理论分支使用 `research/`，代码实验和正式确认使用 `experiment/`。

### 2.1 两种工作粒度

三阶段结构对「一个想法从头走到尾」是合适的，但它假设「一个想法 = 一组分支」。
实际研究里还有第二种形态：**一轮批量出清多个机制族**（例如一次审计同时否证十几个候选）。
把这一轮拆成十几个分支，成本远大于收益，而且分支名无法对应任何单点想法。
因此明确区分两种粒度：

| 模式 | 适用 | 分支形态 | 命名 |
|---|---|---|---|
| **单点模式** | 候选已明确，需要完整走完理论→消融→确认 | 每个想法 1–3 个分支 | `research/<idea>-theory`、`experiment/<idea>-ablation`、`experiment/<idea>-confirmation` |
| **批量筛查模式** | 一轮里并行筛查/否证多个候选，多数预期在理论阶段被否 | **一个**分支，按轮次在同一分支追加 commit | `research/<topic>-screen`（如 `research/second-innovation-screen`） |

批量筛查的附加要求：

- 一个筛查分支持续复用，不因轮次增加而新建分支；轮次体现在 commit 信息和分支内文档目录上。
- 每个被筛查的候选须在文档中单独成节，包含机制、否证判据与结论，便于后续按候选检索。
- 若某候选在筛查中存活并需要实现，**才**从当时稳定的 `main` 另外创建它自己的 `experiment/<idea>-ablation`。
- 已产生的按轮次命名的历史分支不重命名（重命名需改远端与大量文档引用，成本大于收益）；
  其轮次到想法的映射由《研究路线总表》维护。

### 2.2 唯一索引：研究路线总表

工作流本身只定义流程，不记录状态。因此仓库维护一份索引：

- 文件：`docs/研究路线总表.md`
- 作用：记录每个方向的分支、阶段、状态、关键 commit、结论、已消费资源与下一步。
- 约束：**任何阶段门（放行 / 止损 / 确认提交）结束时必须同步更新该表**；
  表内结论必须能在指定入口文档或 commit 中直接复核。

该表同时承担「回写 `main`」的职责：分支结论不回写 `main` 会导致 `main` 上的文档与事实相反，
此类问题已在历史上真实发生过。分支内的决策记录仍是权威产物，总表只是索引入口。

### 2.3 资源用语统一

资源台账中必须区分三个状态，不得混用：

| 用语 | 含义 | 可否使用 |
|---|---|---|
| **已登记** | 在某个协议里预留了站点/时间片/种子 | 否，登记不等于授权 |
| **已授权** | 协议中显式写明可开始使用，且在总表中补记 | 是 |
| **已消费** | 已经读取、训练或评估过 | 否，不能再作为独立确认资源 |

历史文档中出现过把「已登记」写成「已进入历史登记」从而看起来像「已消费」的表述，
导致同一批种子在不同分支状态相反。新增或修订任何资源节时必须按上表用语书写。

## 3. 阶段一：理论探索

### 3.1 创建

理论探索分支直接从 `main` 创建：

```bash
git worktree add \
  -b research/<idea>-theory \
  ~/.herdr/worktrees/PatchTST/research-<idea>-theory \
  main
```

随后可让 Herdr workspace 指向该 worktree。一个本地分支同一时间只能被一个 worktree 检出。

首次推送时设置 upstream：

```bash
git -C ~/.herdr/worktrees/PatchTST/research-<idea>-theory \
  push -u origin research/<idea>-theory
```

### 3.2 应形成的产物

至少记录：

1. 研究问题及其与现有 ST-PatchTST 的关系；
2. 代表性论文、发布日期、代码仓库和许可证；
3. 已有方法的输入、输出、因果边界和计算成本；
4. 候选改进的机制假设，而不是只描述模块拼接；
5. 预期可观测证据、主要风险和否证条件；
6. 数据泄漏检查；
7. 最小可行实现和逐组件消融顺序；
8. 进入代码实验前的明确放行结论。

论文和开源代码只作为证据来源。应保存来源链接和访问日期，区分论文原始结论、代码实际行为和本项目推断。

### 3.3 阶段门

理论探索结束时只能做出以下两类决定：

- **放行**：形成固定的最小方案、基线、消融矩阵、主指标和停止规则，再进入实验分支；
- **止损**：记录不可行原因和已排除方案，推送并归档分支，不创建对应实验分支。

理论止损也是有效研究结果，不应删除其分支或提交。

## 4. 阶段二：实现与消融

### 4.1 从 `main` 独立创建

理论分支主要包含调研资料，因此实验分支应重新从最新稳定 `main` 创建，而不是默认继承整个理论分支：

```bash
git worktree add \
  -b experiment/<idea>-ablation \
  ~/.herdr/worktrees/PatchTST/experiment-<idea>-ablation \
  main
```

如实验必须携带最终理论方案，可采用以下任一种方式：

1. 将最终方案人工整理为实验分支中的简洁协议；
2. 将理论分支的最终方案整理成单独 commit，再用 `git cherry-pick <commit>` 复制该提交。

不要为了获得一份文档而合并整个理论探索分支。

### 4.2 实验范围

消融分支允许：

- 实现候选模型；
- 增加形状、梯度、退化不变性和组件独立性测试；
- 运行 CPU/GPU 冒烟测试；
- 使用训练集和验证集筛选结构及超参数；
- 记录失败候选、运行日志和选择依据。

必须保持对照公平：数据、划分、种子、主干、初始化、优化器、训练流程和最佳模型规则应尽可能一致。测试集不得参与候选选择。

### 4.3 冻结候选

准备进入确认前，应选定一个明确 commit，并记录：

- commit hash；
- 固定模型结构和默认参数；
- 数据版本与划分；
- 选择阶段已经使用的种子；
- 确认阶段尚未使用的新种子或新数据；
- 主次指标、统计方法和放行阈值；
- 失败后的停止规则。

## 5. 阶段三：独立确认

确认分支从消融阶段选定的固定 commit 创建：

```bash
git worktree add \
  -b experiment/<idea>-confirmation \
  ~/.herdr/worktrees/PatchTST/experiment-<idea>-confirmation \
  <selected-commit>
```

这样确认分支完整拥有已选定实现，而消融分支之后的新提交不会自动进入确认分支。

确认阶段只允许：

- 执行预先固定的命令；
- 使用预先保留的新种子、新中心站或新城市；
- 修复阻止实验运行的纯工程错误；
- 汇总指标、复算统计并撰写边界明确的结论。

如果发生工程修复，应记录修复内容，并判断其是否可能改变模型或实验结果；可能改变结果的修复需要重新冻结协议。不得查看确认结果后调整模型，再继续把同一批数据称为“独立确认”。

确认通过后才考虑合并到 `main`。确认失败时，将结果降级为探索证据并归档；若提出新候选，应返回新的消融周期，并使用未被消费的新确认资源。

### 5.1 确认可以在消融分支内完成

独立 `experiment/<idea>-confirmation` 分支是**首选**而非强制形态。如果确认使用的实现与消融分支
最后一笔提交完全一致（即消融阶段选定的 commit 就是该分支 HEAD，之后没有新提交），
可以在该分支上直接执行确认，不必为了形式再开一个分支。选择这种方式时必须满足：

- 在总表中登记 **selected commit hash**、确认阶段使用的资源、预注册阈值与停止规则；
- 在分支内留一份确认记录文档，包含固定命令与结果目录；
- 确认结果不得回流修改结构；若必须修改，则回到 §5 的常规路径，另建 confirmation 分支并使用新资源。

若确认需要携带消融分支之后的新提交、或需要与消融工作并行推进，则必须另建 confirmation 分支。

## 6. Worktree 与分支归档

### 6.1 推送和检查

结束一个阶段前执行：

```bash
git status --short --branch
git push -u origin <branch>   # 首次推送
git branch -vv
git worktree list
```

确保工作区干净，且本地分支具有对应 upstream。

### 6.2 移除 worktree

先关闭对应 Herdr workspace 或其中的进程，再执行：

```bash
git worktree remove <worktree-path>
```

该命令只删除检出的工作目录，不删除本地分支、commit 或远程分支。以后可以恢复：

```bash
git worktree add <worktree-path> <existing-branch>
```

除非明确决定永久丢弃，不要对归档研究分支执行 `git branch -D` 或删除远程分支。失败实验应保留提交、协议和结论，以避免后续重复走同一条无效路线。

### 6.3 索引同步（阶段结束的必做项）

每个阶段门结束时，除推送分支外还必须更新 `docs/研究路线总表.md`：

1. 更新该方向在主表中的状态、结论与实测效应量；
2. 更新分支级明细中的 HEAD 与入口文档；
3. 把本阶段新消费的资源写入资源台账的「已消费」，把新预留的写入「已登记未消费」；
4. 若发现两个分支对同一资源的状态表述冲突，写入总表的问题与风险节，并显式标记未解决，
   不得擅自改写历史分支的结论。

总表条目必须引用可复核的入口文档或 commit；无法复核的结论不要写入。

## 7. 决策速查

```text
提出新想法
  ↓
research/<idea>-theory：只做理论与资料探索
  ├─ 不可行 → 记录止损 → 推送 → 移除worktree并保留分支
  └─ 可行   → 固定最小方案与实验协议
                ↓
experiment/<idea>-ablation：实现、验证集选择、逐组件消融
  ├─ 不成立 → 记录负结果 → 归档
  └─ 候选成立 → 冻结selected commit与确认规则
                     ↓
experiment/<idea>-confirmation：新种子/新数据独立确认
  ├─ 失败 → 降级为探索证据，不复用确认资源调参
  └─ 通过 → 更新报告，审查后合并main
```

上面的每一个箭头两侧（放行 / 止损 / 归档 / 确认提交）都要同步《研究路线总表》。
批量筛查模式走简化路径：`research/<topic>-screen` 单分支内按轮次追加 commit，
只有存活的候选才从 `main` 另开 `experiment/<idea>-ablation`。

## 8. 最低记录要求

每个研究方向无论成功或失败，至少应能回答：

- 为什么提出该方向；
- 查阅了哪些论文和实现；
- 理论机制和可否证假设是什么；
- 使用了哪些数据、种子和指标；
- 哪些信息用于选择，哪些保留用于确认；
- 最终为何放行或止损；
- 对应分支、固定 commit、命令和结果目录在哪里；
- 在《研究路线总表》中对应哪一行、状态是否已同步。
